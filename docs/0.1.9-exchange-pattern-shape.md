## 1. 结论摘要

| 问题 | AE2 1.21.1 / 26.1.2 | Refined Storage 2.0.9 / 3.2.1 |
|---|---|---|
| 一个 pattern 的"耗 N 仙元 → 产 M 资源"怎么表达 | 输入 `IInput[]{ getPossibleInputs()[1~n], getMultiplier()=N }`，输出 `List<GenericStack>{ GenericStack(资源,M) }` | `PatternLayout.external(List.of(new Ingredient(N, List.of(仙元))), List.of(new ResourceAmount(资源, M)))` |
| 多输入 | 支持：`IInput[]` 每项一类输入，各带 multiplier；每项内部还可有多个"可替代物" | 支持：`List<Ingredient>`，每个 Ingredient 内部是"可替代物"列表 |
| 多输出 | 支持：`getOutputs()` 是列表，`getOutputs().get(0)` 是合成索引用的主产物 | 支持：`outputs()` 是列表；`byproducts` 只有 INTERNAL 能用 |
| 数量上限 | 编码表 UI 81 输入 / 27 输出；`encode()` 自身不按槽位截断；`GenericStack` 的 amount 是 long 且**不校验正负** | API 层无上限；玩家编码 UI（Pattern Grid）按 `getProcessingPatternLimit()` 限制（物品=最大堆叠数），程序化构造绕过 |
| 免费配方（0 输入）会不会被拒 | **编码路线拒绝**（`IllegalArgumentException: At least one input must be non-null.`）；**纯 API 路线不拒绝** —— 自己做 `IPatternDetails` 时 AE2 不会拦，必须自己过滤 | **构造即拒**：`PatternLayout` 抛 `Ingredients cannot be empty` |
| 合计结论 | 兑换 pattern 只能走"自定义 `IPatternDetails` + `ICraftingProvider` 节点服务"或"编码 pattern 放进 `PatternProviderLogic` 宿主"；两条路都要自己拒绝免费源脉 | 兑换 pattern 必须挂在 `PatternProviderNetworkNode`（`PatternProvider`）上，由 sink 结算；空原料在构造期就进不来 |

### 2.2 `IInput` 的精确语义 [实测 + 推断]

- `getPossibleInputs()`：模板数组。`CraftingTreeProcess` 构造器**无条件反汇编取 `[0]`**（`iconst_0 / aaload`），所以数组必须**非空**，否则 NPE。
- `getMultiplier()`：一次合成消耗的数量。`CraftingCpuHelper.extractPatternInputs` 按 `details.getInputs().length` 建 `KeyCounter[]`，再按 multiplier 从任务库存取料 [实测，见 2.4]。
- `isValid(AEKey, Level)`：判断网络里的具体 key 能否代入。
- `getRemainingKey(AEKey)`：容器物品语义。`CraftingTreeProcess.updateLimitQty` 里 `getRemainingKey(...) != null` ⇒ 置 `containerItems = true; limitQty = true` [实测]。返回 `null` 表示"完全消耗"，这正是仙元需要的语义。

AE2 自己的 `AEProcessingPattern$Input`：`template = [GenericStack(key,1)]`、`multiplier = 真实数量`、`isValid = key.matches(template[0])`、`getRemainingKey = null` [实测]。**兑换 pattern 直接照抄这个形状即可。**

该内部类的构造与四个方法逐条反汇编（形状的权威样板）[实测]：


### 2.5 路线对比

| | A：编码 pattern | B：自定义 `IPatternDetails` | A'：自定义编码物品（`EncodedPatternItemBuilder`） |
|---|---|---|---|
| 需要方块宿主 | **要**（`PatternProviderLogicHost`） | 不要（挂在仙窍控制器节点的 `ICraftingProvider` 服务上） | 要（样板物品本身要在某个样板宿主里） |

## 4. 仙元如何进入配方（本文件的第二个问题）

### 4.1 不可绕过的约束

仙元是玩家账本（`ImmortalStoragePlayerData#getImmortalYuan()`，long）[实测，源码]，不是物品堆。而两侧的合成模型都要求原料可被"抽取"：

- AE2 [实测]：CPU 先 `extractPatternInputs` 从**任务库存**按 multiplier 抽料，再调 `pushPattern(details, inputs)`。抽不到就根本不会 push。
- RS [实测]：`acceptsIterationInputs` 先从 **root storage** `extractAll`，抽到才把结果交给 sink。

所以只有两种形状。

### 4.2 形状 a：把账本投影成可抽取的存储通道

| | AE2 | RS |
|---|---|---|
| 落点 API | `AEItemKey.of(ModItems.IMMORTAL_YUAN.get())` 当 pattern 原料（物品投影）；或新建 `AEKeyType`+一个 `MEStorage` 实现（账本投影） | `ItemResource.ofItemStack(仙元物品)` 当 `Ingredient` 的 `ResourceKey`；由 `CompositeAwareChild` 存储实现把网络读写转成账本读写 |
| 本仓库现状 | 物品投影：`compat/ae2/XianqiaoAe2CraftingProvider#yuanKey()` 返回 `AEItemKey.of(ModItems.IMMORTAL_YUAN.get())` [实测，源码]。网络里必须先有这个物品，CPU 才抽得出来 | **已实现**：`compat/refinedstorage/RsManagerCurrencyStorage` 只有一个 `ItemResource`，`getStored()/getAll()` 返回 `getImmortalYuan()`，`extract(EXECUTE)` 调 `consumeImmortalYuan`，`insert(EXECUTE)` 调 `depositImmortalYuan` [实测，源码] |
| 限制 | ① 仙元物品必须真的可被 `extract`（否则计划阶段显示可做、执行阶段抽不到）；② 账本 → 物品的双向一致性由投影层负责，否则计划/执行不一致；③ `GenericStack` 不校验数量，仙元数量写错不会被 API 挡住 | ① 投影必须挂在网络 root storage 上（`CompositeAwareChild`），否则 `extractAll` 看不到它；② `getStored()` 与真实账本必须同步（`RsAmountPolicy.advertised` 已做边界钳制）；③ 这会**把仙元变成可从 RS 终端抽出的资源**（`RsManagerCurrencyStorage` 类注释已把它列为待用户裁定的开放风险） |

### 4.3 形状 b：自定义 sink/provider 直接扣账本

| | AE2 | RS |
|---|---|---|
| 落点 API | `ICraftingProvider.pushPattern(details, KeyCounter[])` 里直接调 `SourceChargeRegistry` / 账本 | `ExternalPatternSink.accept/insertAll(Pattern, Collection<ResourceAmount>, Action)` 里直接扣账本 |
| 可行性 | **部分**：CPU 已经先抽走了一份"输入"，如果 `getInputs()` 为空则 `extractPatternInputs` 抽不到任何东西也不会拒绝 ⇒ 免费/白给。所以 b 只能在"输入是一个可抽取的占位/真实资源"的前提下用 | **退化**：sink 收到的料**已经从 root storage 抽走**。若 Ingredient 指向一个与账本无关的占位资源，等价于"用占位资源当门票再私下扣账本"，账实不符；实际可用的形态仍是 a |
| 本仓库现状 | 已采用**a+b 混合**：pushPattern 里 `depositImmortalYuan(yuanPerBatch)` 把推入的仙元物品还回钱包，然后走源脉 `extract` 扣费，净额为零；类注释已列出两处残窗（存款被部分接受、源脉少产不退）[实测，源码] | 采用 `a`（`RsManagerCurrencyStorage` 投影）+ sink 里按 `outputsPerBatch` 产出 |

### 4.4 取舍

- **AE2**：a+b 混合（物品投影 + 钱包回归 + 源脉扣费）是当前唯一不引入自定义 `AEKey` 的实现；代价是"钱包-物品"两次记账之间的残窗，需要 `SourceChargeRegistry` 暴露"预留/结算"才能根治（属后续 API 工作，不在本文件范围）。
- **RS**：必须走 a；`RsExchangeProviderNode` 的 sink 只在**已抽到仙元**之后被调用，产出直接 insert 到 `StorageNetworkComponent`，由 `ExternalTaskPattern.afterInsert` 记账 [实测，源码注释 + 字节码]。
- 两侧都**不要**试图用"0 输入 pattern + 直接在 pushPattern/sink 里扣账本"来模拟免费兑换：AE2 不会拒绝（会白给），RS 在构造期就抛异常；且免费源脉的 `storageVisibleUnits()` 返回 `Long.MAX_VALUE`（源码第 549 行 `if (plan.isFree()) return Long.MAX_VALUE;` [实测]）—— 一旦 pattern 无输入，网络可以零成本无限取料。

## 6. 免费源脉（`yuanPerBatch == 0`）必须在两侧自行拒绝

**数据层允许免费** [实测，源码]：`source/SourceExchangeOffer` 只要求 `yuanPerBatch >= 0`、`outputsPerBatch > 0`；`paid()` 定义为 `yuanPerBatch > 0L`。

**为什么不能发布** [实测，源码]：`SourceVeinBlockEntity#storageVisibleUnits()` 第 549 行 `if (plan.isFree()) return Long.MAX_VALUE;` —— 免费源脉对网络报告无限可见量。

于是：
- 若发布一个 **0 输入** pattern：AE2 的 `ICraftingProvider` 路线**不会**拒绝（§5.1 第一行），CPU 会认为该产物由"零成本"可得；RS 则在 `PatternLayout` 构造期直接抛异常（§5.2）。
- 结论：**两个 provider 都必须过滤免费 offer**，且在过滤处留日志。本仓库现状（源码核对，非本轮修改）：`XianqiaoAe2ExchangePattern.of(...)` 在 `yuanPerBatch() <= 0` 时返回 null；`RsExchangeOfferPatterns.pattern(...)` 以 `!offer.paid()` 返回 null。
